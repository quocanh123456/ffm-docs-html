Quy trình review và tiến độ review task, ticket

Mở trang này để biết task hoặc ticket của mình đang ở bước nào: chờ dev sửa, chờ review lại, hay đã hết lỗi chặn merge. Bảng tiến độ tự cập nhật mỗi giờ khi có thay đổi; task và ticket xem ở 2 tab riêng vì cách xử lý khác nhau.

01

Tiến độ review

Task và ticket anh SH review. Chọn tab, bấm nút để lọc theo bước, gõ tên GitHub để xem PR của mình.

Vòng: số lần anh SH đăng review có tóm tắt trên PR. Lỗi còn mở: comment review của anh SH chưa được bấm Resolve, đếm theo mức P0 / P1 / P2 / Nit. Commit không tính commit gộp nhánh gốc vào PR.

Ý nghĩa từng bước

  • Chờ dev sửa Review gần nhất còn lỗi P0 / P1 hoặc là REQUEST_CHANGES, chưa có commit mới sau đó. Việc của dev.
  • Dev đã cập nhật, chờ review lại Có commit mới sau review gần nhất. Lượt kiểm tra kế tiếp (mỗi giờ) sẽ review lại.
  • Chưa có link PR trong thread Chỉ ở tab Ticket: thread ticket chưa có link PR nào, hệ thống chưa có gì để review.
  • Đang review / Chưa có review trên GitHub Đang chạy review, hoặc PR chưa có review nào được đăng.
  • Không còn lỗi chặn, chờ merge Không còn comment P0 / P1 chưa Resolve và review gần nhất không phải REQUEST_CHANGES.

Task chưa có PR mở

    02

    Quy trình review task

    Lặp lại từ bước 2 tới bước 5 cho tới khi hết lỗi P0 / P1

    1
    Dev mở PRTiêu đề PR kết thúc bằng #<số task>. Panchat tự gắn nhãn dev:code-reviewing.
    2
    Tự phát hiện cập nhậtMỗi giờ kiểm tra commit, comment GitHub, comment Panchat mới hơn lần review trước.
    3
    Review toàn bộ PRĐọc lại toàn bộ thay đổi so với nhánh gốc (không chỉ commit mới), chạy test có trong PR.
    4
    Đăng REQUEST_CHANGESMỗi lỗi 1 comment có mức P0–Nit. Panchat tự chuyển nhãn sang dev:request-changes.
    5
    Dev sửa và trả lờiSửa kèm test, tự chạy /super-review, push, comment dòng SELF_REVIEW: vào PR, trả lời từng comment. Quay lại bước 2.

    Ô màu vàng là việc của dev; các ô còn lại do người review và hệ thống tự làm.

    6
    Hết lỗi P0 / P1 → mergeAnh SH merge PR. Nhãn task chuyển sang dev:reviewing để BA kiểm tra.
    7
    BA kiểm tra đạtBA đóng task trên Panchat.
    8
    DeployAnh SH deploy lên prod; dev không tự deploy.

    Task có nhiều PR (BE + FE + mobile) thì mọi PR đều phải hết lỗi P0 / P1 mới merge.

    03

    Quy trình review ticket

    Ticket là tin nhắn hỗ trợ trong channel (vd ffm_support) giao cho anh SH; không có nhãn dev:*

    1
    Dev dán link PR vào threadHệ thống chỉ tìm PR qua link GitHub trong thread ticket, không theo tiêu đề PR. Chưa có link thì ticket không vào lượt review.
    2
    Tự phát hiện cập nhậtMỗi giờ kiểm tra tin mới trong thread, commit và comment mới trên các PR có link trong thread.
    3
    Review toàn bộ PRGiống task: đọc lại toàn bộ thay đổi so với nhánh gốc, chạy test có trong PR.
    4
    Đăng REQUEST_CHANGESĐăng trên GitHub như task. Ticket không có nhãn nên không đổi nhãn: dev theo dõi qua GitHub hoặc tab Ticket ở trên.
    5
    Dev sửa và trả lờiSửa kèm test, tự chạy /super-review, push lên đúng PR đã dán link, comment dòng SELF_REVIEW: vào PR. Quay lại bước 2.

    Khác với task: không cần #<số> ở tiêu đề PR, không đổi nhãn; PR mới mở thêm thì dán thêm link vào thread.

    6
    Hết lỗi P0 / P1 → mergeAnh SH merge PR.
    7
    DeployAnh SH deploy lên prod.
    8
    Đóng ticketTrả lời link commit trong thread rồi đóng ticket.
    04

    Mức lỗi và điều kiện merge

    Chỉ P0 và P1 chặn merge

    P0

    Chặn merge

    Sai dữ liệu, lộ dữ liệu / bảo mật (thiếu lọc app_id, log lộ token), làm hỏng prod, test đang fail, lệnh debug còn sót (IO.inspect, dbg()).

    P1

    Chặn merge

    Lỗi logic sẽ gặp trong thực tế. Mọi lỗi về test luôn là P1: thiếu test cho yêu cầu / nhánh / dòng code mới, test viết sai, kiểm tra kết quả quá lỏng, dữ liệu mẫu phụ thuộc môi trường. Yêu cầu của task làm dở (“làm đợt 2”, “sau khi #N merge sẽ làm tiếp”) cũng là P1.

    P2

    Không chặn

    Code khó bảo trì: lặp code, số viết cứng, đặt tên khó hiểu. Nên sửa trong cùng PR.

    Nit

    Không chặn

    Định dạng, câu chữ, gợi ý. Lỗi người review chưa chắc chắn cũng ghi Nit kèm “cần dev xác nhận”.

    i

    Lỗi có sẵn trên nhánh gốc (dòng code không do PR viết ra) được ghi riêng trong phần tóm tắt review, không chặn merge. Dev chọn sửa trong PR này hoặc PR riêng.

    05

    Dev cần làm gì để review nhanh hơn

    Mỗi điểm dưới đây giảm 1 vòng review

    Đặt tiêu đề PR đúng

    Bắt buộc

    Task: tiêu đề kết thúc bằng #<số task Panchat>, vd feat: kiểm kê hàng #468. Thiếu phần này thì hệ thống không tìm thấy PR của task, task không vào lượt review.

    Ticket: dán link PR vào thread

    Bắt buộc

    Mở PR cho ticket thì dán link PR vào thread của ticket đó. Thiếu link thì ticket không vào lượt review dù PR đã mở.

    Tự review và dán kết quả vào PR

    Bắt buộc

    Trước khi push bản sửa: đứng ở nhánh PR trên máy mình, commit hết rồi gõ /super-review <link task hoặc link thread ticket> trong Claude Code (lệnh chỉ review, không đăng gì lên GitHub, không đổi nhãn). Sửa hết lỗi lệnh báo, push, rồi comment nguyên dòng SELF_REVIEW: HEAD … · P0 … · P1 … lệnh in ra vào PR trước khi báo review. Review của techlead kiểm tra dòng này đầu tiên: thiếu hoặc SHA khác HEAD đã push thì review ghi "Thiếu kết quả tự review" ở đầu (từ 16/11/2026).

    Viết test cùng commit sửa

    Nên làm

    Mỗi lỗi P0 / P1 / P2 có mục Test cần viết (dữ liệu dựng trước, thao tác, kết quả phải kiểm tra). Viết test đó trong cùng commit sửa lỗi, để vòng sau không phải nêu lại “bản sửa chưa có test”.

    Trả lời từng comment

    Nên làm

    Ghi đã sửa ở commit nào, hoặc lý do giữ nguyên. Vòng sau người review đối chiếu từng comment với code mới.

    Làm đủ yêu cầu trong 1 PR

    Lưu ý

    Phần yêu cầu hẹn “đợt 2” trong cùng task vẫn tính là thiếu (P1); làm tiếp trong chính PR đó, không mở task riêng.
